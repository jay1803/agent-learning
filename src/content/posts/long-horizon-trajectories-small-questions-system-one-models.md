长程智能体评估可以先用代码提取每个问题所需的证据，再让 System One 模型作出判断，从而以更低的成本和延迟覆盖每一次运行。截至 2026 年初，OpenAI 的 API 每分钟处理超过 150 亿词元，长程智能体在推理调用中的占比还在上升。团队需要从越来越长的轨迹里回答许多小问题，例如用户在某一轮是否表现出挫败感，智能体是否尝试过恶意行为，甚至是否只是考虑过。这些判断用于监控智能体流量、筛选强化学习数据集，也用于批量转换轨迹数据。前沿大语言模型或完整智能体可以通读轨迹，但用它们回答局部问题往往耗时且昂贵，完整轨迹又常常超出小模型的上下文窗口。Judgment Labs 的 @Unhingexd 和 @andrew_li03 提出，先用代码提取用户消息、某次工具调用的输出等证据，就能把离线分析从数小时缩短到数分钟，也能在智能体开始考虑恶意行为时及时发现并介入。成本下降后，团队可以逐条评估轨迹，找出所有表现出挫败感的用户及其身份，并用轨迹标签为整个历史数据建立索引，以更低的成本、更准确地回答自然语言查询。

TypeSafe 把这类决策模型称为 **System One 模型**。它接收一份状态和一个指定答案类型的问题，直接返回代码可用的结构化决策。TypeSafe 的首款模型 Jev 据称已被 30% 的《财富》500 强企业使用。Workday 用它随用户输入实时构建界面，Glean 的搜索助手用它即时作出决策，Judgment Labs 工程师的 Minecraft 智能体则用它决定战斗还是逃跑。用于评审时，一轮用户消息也可以对应一个独立的分类问题，直接输出用户是否表现出挫败感的判断。

直接返回决策省去了逐词元生成。在真实编程智能体轨迹的测试中，Jev 的调用延迟中位数为 0.15 秒，GPT-6 Luna 读取相同证据需要 1.7 秒，读取完整轨迹需要 6.9 秒。自托管还有可能进一步降低延迟。Jev 的未缓存输入词元单价约为 GPT-6 Luna 的三分之一，也没有输出词元费用。它为每个选项返回概率，并提供一个 0 到 1 的置信度分数。概率均匀分布时分数为 0，全部集中在一个选项上时为 1，代码可以据此接受结果或转交其他评审器。TypeSafe 用于校准决策的强化学习方法 RLCD 训练 Jev 同时给出决策和校准过的概率。跨大量预测看，获得 80% 概率的答案应当约有 80% 正确。许多较新的大语言模型没有开放词元概率，模型自行写出的置信度又会受训练数据中的表达模式影响。比如让模型在 1 到 100 之间随机选数，它常选 42，因为这个数字作为《The Hitchhiker’s Guide to the Galaxy》中关于生命、宇宙及万物的答案频繁出现在训练文本里。重复运行同一评估可以用答案的一致程度估计置信度，但操作繁琐，成本也会随调用次数成倍增加。

一项评审适合交给 System One 模型，需要同时满足三个条件：判断本身足够简单、无需书面解释、所需证据足够少。前两项由评审标准决定，第三项还取决于工程上能否从可预知的位置提取证据。Jev 返回选项和概率，评审理由需要另行取得。它默认每次最多读取 64K 词元，长上下文模式可扩展至 262K，但 TypeSafe 指出该模式更慢、准确率更低，长程轨迹仍可能超限。对于「智能体是否解决了问题并清楚地沟通？」这种需要判断两件事的标准，可以拆成「智能体是否完成了用户要求的任务？」和「智能体是否清楚解释了自己做过什么？」两项独立评估。

**预处理要求证据可定位、有界且充分。** 可定位意味着代码能可靠地找到证据，例如用户最开始的三轮消息，或某次特定工具调用之后紧接的内容。有界意味着提取结果能稳定落在预设上限内，例如模型的上下文窗口。充分意味着提取内容包含作答所需的全部信息。用户开头两轮可以说明最初想做什么，要判断请求后来有没有改变，就还需要看后续对话。Judgment Agent 先读每个评审器的标准，再查看项目的真实轨迹。三项条件都成立时，它编写预处理代码，在真实轨迹上测试后接入评审器。条件不成立时，系统继续使用能查看更多轨迹内容的 Agent-as-a-Judge。

充分性最难验证。代码能检查证据是否找到、是否超限，提取范围外的关键信息却可能被漏掉，模型也可能据此给出高置信度答案。Judgment Labs 在启用预处理前，先用预处理后的评审器给一批样本打标签，再由能阅读完整轨迹的评审者标注同一批案例，优先由人工完成。随后逐个检查判定不一致的案例。如果决定答案的证据落在提取范围之外，该标准就继续交给 LLM-as-a-Judge 或 Agent-as-a-Judge。

给用户的开场请求做主题分类就适合这种方法。编程智能体的开场请求可以分成修复错误、开发功能、重构和其他。Judgment Labs 用一家客户的分析智能体做了类似测试，共使用 87 条轨迹，最长约 90 万词元。Judgment Agent 发现，主题证据始终在用户开头几轮，通常就在第一条问题里，于是用完整轨迹评审者的标签校验提取证据的充分性。测试比较了四种配置。Agent-as-a-Judge 自行探索完整轨迹，LLM-as-a-Judge 在一次调用中读取整条轨迹，另外两种分别使用大语言模型和 System One 模型，沿用相同的评审标准和类别，只读取代码提取的用户开场问题。这次测试没有发生回退，展示的是最佳情形。生产中，证据超限、轨迹结构不符合预期或 System One 模型置信度不足，都会触发向 Agent-as-a-Judge 的回退。单次回退与常规智能体评审成本相同，计入回退后，客户现有配置的评估成本仍最多降低了 80%。

单个评审器可能需要在数千条客户轨迹上执行生成的预处理代码。Judgment Labs 用 Cloudflare Isolates 做轻量沙箱，由已部署的 Worker 接收请求，运行时加载 Dynamic Worker 执行脚本。Dynamic Worker 无法出站联网，只能通过 RPC 存根请求数据，由受信任的 Worker 通过 vSQL 执行经过身份验证的只读查询，凭据始终留在沙箱外。脚本可以编写查询文本，租户范围则由已部署的 Worker 根据评估请求提供的组织、项目和轨迹 ID 决定。

最初使用的 `.load()` 每次执行都会新建一个 Dynamic Worker，Cloudflare 又将创建费用与 CPU 时间分开计费，脚本即使运行得很快，执行数千次也会累积创建费用。同一个评审器处理不同轨迹时使用同一份代码，因此 Judgment Labs 把脚本设为不可变，赋予稳定 ID，再用 `.get()` 复用缓存的 Worker。原文用同一脚本一天执行 1,000 次作比较，采用每个 Worker 每天 0.002 美元的费率，未计入套餐内额度以及在其负载下很低的请求和 CPU 费用。复用时，顶层变量等主函数之外的状态可能残留到下一次执行。每份脚本只属于一个评审器，状态残留不会造成跨客户数据泄漏。由于 Cloudflare 不保证每次都复用，依赖全局状态可能让同一条轨迹得到不同结果，Judgment Agent 因此被要求避免在脚本中使用全局状态。

评审标准变更时，系统将其视为评审器的新版本，先关闭 System One 模型，再由 Judgment Agent 重新判断该提取什么证据。轨迹结构发生明显变化时，脚本校验会识别不匹配并触发回退。对尚未触发校验的渐进变化，Judgment Agent 定期抽取近期轨迹，用 Agent-as-a-Judge 重跑并比较判定。一致率下降时，它会重新检查证据是否充分，并更新预处理代码。

公开测试使用 SWE-chat 中开源开发者的真实编程智能体会话。Judgment Labs 抽取了 256 条轨迹，每条至少包含 100 次智能体工具调用和 3 条用户消息，每个代码仓库最多入选 3 条。样本的工具调用次数中位数约为 180，轨迹长度中位数约为 117K 词元，最长约为 757K。实验保留了六项仍需语义判断、但证据可由代码定位的标准，由能读取完整轨迹的 Judgment Agent 抽查确认提取内容足以作答。其余标准大多因证据不足被淘汰，其中多数只在少数案例里出问题，决定答案的信息恰好落在提取范围之外。实验对每种配置各执行 1,536 次评估，每次调用只回答一项标准。三种配置分别是以高推理强度读取完整轨迹的 GPT-6 Luna、只读取提取证据的 GPT-6 Luna，以及读取相同证据的 Jev 1.13。

预处理把输入长度中位数压到不足 500 词元。以 Opus 5.5 的判定为基准标签，Jev 读取提取证据的一致率为 82.5%，GPT-6 Luna 读取完整轨迹的一致率为 79.8%。Jev 方案的模型成本约为完整轨迹方案的 **1/600**，延迟约为 **1/47**。GPT-6 Luna 改读提取证据后，一致率为 81.4%，模型成本已低于读取完整轨迹时的 1%。大部分成本降幅来自预处理，Jev 在此基础上进一步降低成本和延迟。分项看，Jev 在显式约束、措辞保留和计划上得分最高，读取提取证据的 GPT-6 Luna 在命令用途上得分最高，读取完整轨迹的 GPT-6 Luna 在用户挫败感上得分最高。

Judgment Labs 预计，轨迹长度会比上下文窗口增长得更快，提取局部证据的方法会覆盖更多评审标准，同一份预处理输出也可供不同模型使用。随着智能体承担更重要的工作，人力将无法逐条审阅所有轨迹。能够存储、搜索轨迹并在全部数据上运行模型的基础设施，可以让团队对每条轨迹低成本、可靠地提问，并批量执行由模型驱动的数据转换。作者预计，团队很快会在这些数据上运行数万个 System One 模型和大语言模型，分析智能体实际做了什么，筛选后训练和强化学习数据集，并推动智能体自我改进。两位作者感谢 @typesafeai 团队审阅文章，也期待 Jev 用于更多应用。
