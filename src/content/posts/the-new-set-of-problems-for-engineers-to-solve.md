这篇 X Article（2026-10-26，Katelyn Lesse）是写给正在经历“身份危机”的软件工程师的。核心论点：**多 agent 系统的能力上限，不取决于模型，而取决于工程师能否解决它带来的一组新问题**。agent 已经从人盯着的聊天，走到云端长时间运行，再到编排者派子 agent、或让 agent 承担评分、顾问、“做梦”等非执行角色；有人开始用成千上万个持续工作的 agent 去做严肃研究、科学发现和硬件设计。模型会继续变强，但只有基础设施、身份与权限、安全隔离、监控与熔断这四块被解决，世界才敢把这种能力用在治愈疾病这类好结果上。所以作者认为现在是做工程师最有意思的时刻之一。

## 一、基础设施要演进

- 行业一直建在 Kubernetes 上，它为**无状态、可复制的应用**或**稳定编号的有状态 pod 集合**设计。agent 完全不同：本质是**隔离的、有状态的、单实例**负载。
- agent 会在两段工作之间空闲任意长时间，大量时间花在等待工具、模型推理、其他 agent 或人的输入上。不同负载的诉求互相冲突：有的要快速启动，有的要避免浪费算力，有的要极大规模。
- 已有人在推进，比如 AI 基础设施公司在做新的文件系统和沙箱产品，Google 团队在做名为 Agent Substrate 的新运行时，但作者认为还有大量问题没想清楚。

## 二、身份与访问

- **认证**（识别是哪个 agent 做了某个动作）相对好办：可以借用微服务时代已经打磨过的积木，例如用短期证书的工作负载身份代替静态密钥。
- **授权**（允许 agent 做什么）要开放得多。很多 agent 代表人行事（on-behalf-of，OBO），直接用人的身份和凭证访问系统，这里已经有一个问题：如何区分动作是 agent 做的还是本人做的。
- 更深的问题是**同意**：多 agent 系统一跑就是几周，人怎样才算真正批准了 agent 能做什么？工具调用自动批准之类的平台功能有帮助，但在大规模下需要更深的权限设计。
- 更不成熟的是**拥有自己身份的 agent**，以及 agent 之间如何互信：一个 agent 请另一个 agent 做事，后者凭什么信它？

## 三、安全与隔离

- 过去几个月，尤其是最近几周，漏洞被发现的速度已经快过行业修补的速度，而且很多在大家都依赖的核心软件里。再设想成千上万个持续运行的 agent 跑在这些软件上，写不可信的代码、读不可信的内容，未修补的漏洞就危险得多。作者认为工程师最重要的事情之一，是想办法加固内核、浏览器、运行时和常用库。
- 多 agent 还多一层风险：**被攻破的 agent 会把注入的指令传给协作的其他 agent，这些指令还可能进入记忆，被未来的 agent 当真**。于是要问“第一个 agent 被攻破时，整个系统有多少处在危险中”。爆炸半径成为真实问题，所以 agent 应该在强隔离的沙箱执行环境里采取行动。

## 四、监控与叫停

- 需要**跨 agent 的 OTel 追踪**，并保证 agent 永远不能修改自己或其他 agent 的 trace。
- 需要监控系统能触发的**熔断开关**，真正一次性停掉整个系统，并吊销它的凭证。
- 最难的是**判断系统何时走偏**：出于好意的坚持解决问题，看起来可能和恶意行为很像。比如反复尝试访问不在白名单上的域名。

## 结论

作者对感到焦虑的工程师说：你的知识和技能，恰恰决定这些问题能否被解决、多 agent 系统能否去解决世界上最难的问题。这些领域大量空白，值得深入学习、形成自己的观点。
