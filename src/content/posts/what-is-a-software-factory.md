这篇 X Article（2026-07-10，Chamath Palihapitiya，8090 公司）的核心论点：“软件工厂”这个词正被 AI 公司大量借用，因为它暗示企业想要却得不到的**工业级可靠性**；但工厂的本质从来不是工具或提效手段，而是**一个接收输入、产出成品、并为成品质量负责的生产系统**——福特卖给你的是一辆车而不是扳手和零件，车坏了福特召回。最反直觉的判断：**代码生成本身会加速系统腐化**，因为企业软件的瓶颈从来不是写新代码，而是每周几十个人改动带来的漂移；没有治理的 agent 车队几年就能造出人工花了四十年才堆出来的烂摊子。

## 开头的案例

8090 拆解了一家大型机构的计费引擎：**1800 万行 COBOL 和汇编**，没人能完整理解；他们用自己的软件工厂在 **40 天**内把它逆向成 **10 万多条英文业务规则**。

## 这个词比多数人以为的老

- 1969 年日立开设 “Software Works”，是一座真正的工厂：统计质量控制、按每千行代码度量缺陷率、标准化流程、管理层为产出质量负责。东芝、NEC、富士通跟进，1970–80 年代日本软件工厂交付了史上最可靠的一批代码，支撑银行、铁路、电力几十年。
- 2004 年两位微软架构师出版《Software Factories》，主张像造车一样造软件：用经过验证的组件、可重复的生产线，靠前期设计而非下游救火来控制变异。美国空军的 Kessel Run 至今为国防部构建和运营任务软件，坏了由他们负责。
- 六十年来唯一不变的是：工厂是生产系统，并为产品担责。作者认为现代软件工厂也必须遵守这个标准。

## 五条检验（缺一条就不是工厂，多半是开发工具）

1. **从业务意图出发**：输入是用业务语言表达的需求、规则、监管约束和期望结果。如果输入是工程师写给工程师的 Jira 工单，那只是在现有流程上加了一把电动工具。工厂的意义在于客户描述产品，工厂负责想办法生产。
2. **在持续变更中保持一致（最难、也最少被谈及）**：需求与文档漂移，文档与代码漂移，代码与测试漂移，二十年复利下来就是那台 1800 万行、维护合同每年涨 5–8%、组织不敢改自己软件的计费引擎。**如果 agent 针对不同步的规格产出十倍代码，就是以前所未有的速度制造漂移**。真正的工厂把意图、规格、代码、测试和生产行为作为**一个受治理的整体**保持同步：改需求，代码跟着变；热修代码，需求随之更新。检验方法：让供应商在真实系统上现场演示这个闭环，做不到的就是在卖代码生成。
3. **不依赖任何特定的人**：同一个编码 agent 交给两位工程师，产出差异巨大，取决于谁写 prompt、谁审 diff、谁发现错误——这种方差对工具可以接受，对生产系统则是否决项。工厂要做到无论谁当班都有可预测的速度和质量（日立统计控制的本意：**质量是生产线的属性，不是操作员的属性**）。办法是让知识在系统里而不是在个人身上复利：新人加入，工厂把已学会的一切交给他；有人离开，什么也不会被带走。计费引擎变得不可读不是因为代码烂，而是理解代码的知识在人身上，而人会换。这不是说人不重要——工厂总有具体的人为产出负责，只是不依赖任何一个不可替代的英雄；需要英雄才能运转的系统既没有问责也不是工厂。
4. **每个产出单元可追溯**：真实工厂里每个零件都有批号，出问题可以追到批次、机器和班次。受监管行业要求软件也这样，这也是它们最慢采用 AI 编码工具的原因——“模型写的”不是审计员接受的答案。软件工厂要把审计轨迹作为生产的**副产品**：这条规则存在是因为这条需求，由此人批准，在此次变更中实现，经此测试验证，于此时部署。事后补写的文档不算。
5. **有人为成品负责（区分工厂与工具的关键）**：计费算错、交易系统出错、生产校验放过坏零件时，要有具体的人出来负责、修复并承担成本。作者读过大量 AI 工具合同，知识产权条款写好几页，责任条款通常只有一句：产出按原样提供，验证是你的事——这对工厂来说完全不合格。案例：一家上市健康险公司把应付理赔规则做成确定性的前置过滤器，转给按件收费供应商的理赔减少 80% 以上，四年避免了 2000 多万美元支出——作者认为只有干活的一方对结果负责时才会出现这种数字。

## 哪些不是工厂

- **编码 agent**，再好也是工具：输入是工程任务，输出是代码，把所有验证和责任转嫁给客户的工程师；把一群编码 agent 叫作工厂也改变不了这一点。
- **agent 编排面板**是监督工具，让你更容易看着 agent 干活。
- **基准测试**是工具的度量装置，高分只说明擅长被测任务，不能说明系统在人和 agent 混合团队连续改动两年后是否仍然一致。

## 为什么现在要较真

生产软件的成本正在崩塌，而**生产成本崩塌时，价值会流向能为产出提供保证的一方**，历次工业化都是如此。抢用“工厂”一词的初创公司本能地明白这一点，但很多只想借用工业生产的信誉，却不接受当初造就这种信誉的义务。他的建议：别看 demo 和基准，问每个软件工厂一个问题——**系统在生产中坏了，谁接电话**？软件工厂的答案必须是“我们”。

## 局限

- 作者是 8090 的创始人，五条检验几乎是为自家产品量身定做的定义，文章也是营销文；1800 万行 / 40 天 / 10 万条规则、2000 万美元节省都是公司自述，无法核实。
- 第二条“意图、规格、代码、测试、生产行为同步为一个整体”是最核心的主张，但文章没有说明怎么做到，只要求读者去问供应商。
- “责任在供应商”的模式对外包和交付成本、合同结构的影响，文章没有展开。
