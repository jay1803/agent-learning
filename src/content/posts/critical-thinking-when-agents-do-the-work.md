**代理可以代做任务和大量核查，独立判断和交付责任仍由人承担**。 批判性思维原本要求人带着谦逊的好奇心和适度的怀疑接触新信息，听过不同观点再形成自己的判断。Addy Osmani 支持同时运行多个代理会话，也预期模型会继续进步。过去，大部分思考和审美判断发生在从问题到答案的过程中，如今这段时间缩短到以秒计。模型越强，明显错误越少，流畅且大体正确的回答越容易让忙碌的人放松警觉，觉得无须再看一遍。即使同时运行许多代理，最后看这些输出的也只有你这一双眼睛。工作流程越来越少迫使人停下来思考，批判性思维就得主动安排进日常工作。

Osmani 每天都在做**认知卸载**，把任务交给 AI，同时保留对结果的判断权和责任。滑到**认知依赖**时，工具的输出直接成了下一步的输入，原本待检验的答案变成了前提。到了沃顿商学院的 Steven Shaw 和 Gideon Nave 所说的**认知投降**，人悄悄把 AI 的输出当成自己的结论，觉得无须检查。每一步都很小，当时也显得合理，所以滑坡很难察觉。上一次认真读完，下一次只略读，再下一次只扫结构，直到有人问起其中一行，自己借助代理也解释不清。能否借助代理解释答案，是判断自己是否已经交出判断权的一条界线。

认知债务往往要等到需要运用对系统的理解时才显现。Margaret-Anne Storey 谈过团队对共同系统理论的理解如何逐渐瓦解。Jeremy Twei 提出的**理解债务**描述了代码中的同一现象。代码库看起来整洁，测试也通过，直到要改动系统时才发现没人理解它。只看策略文档的目录就签字，或没弄清规格说明里的具体要求就批准，也会积下同样的债务。大型代码库很难被任何人完整掌握。Claude Code 团队公开说过，他们需要弄懂哪一部分，就请 Claude 解释哪一部分。只要知道自己缺哪块理解，并能按需重建局部心智模型，这笔债就比许多工程师预想的更容易补救。

是否完全委托，取决于错判的代价由谁承担、代价有多大。Osmani 录制课程时来不及逐条读评论，就让 AI 从三家评分相近的酒店里选出录制地点。结果符合需要，他愿意再这样做。至于怎么投资家庭资金、怎么给孩子提职业建议、工作中该做什么产品或功能、哪些变更会影响哪些用户、成果能否安全发布，他会自己保有对决策过程的理解。

在可以直接问代理下一步该做什么之前，Osmani 常问自己四个问题。“我怎么知道自己在解决正确的问题？”“我怎么知道自己的解决方式是对的？”“有什么证据支持我的结论？”“我怎么知道已经做完了？”再朴素一点，就是逐一问谁、什么、在哪里、为什么、什么时候、怎么做，用这些维度把容易忽略的信息带回视野。现在，他把自问放进与代理协作的几个关口。

- **提问前，我形成自己的假设了吗**？ 有一定难度的任务，先写下或在脑中形成一个可修正的猜测。读完措辞流畅的答案后，其他可能性往往更难想起来。完全没头绪时，可以做 Thariq Shihipar 所说的“盲点排查”，把已知情况交给模型，请它找出自己还没意识到的问题。
- **我是请它帮我思考，还是把思考交给它**？ 两种做法都可以，前提是自己清楚在做哪一种。
- **在什么条件下，这个结论会是错的**？ 找出条件后实际检验。一次能亲自做的测试，比模型自报的置信程度更有价值。
- **我有没有从另一个角度听过反方论证**？ 对开放问题已有强烈立场时，请多个模型各自为反方辩护，读完再形成自己的判断。
- **面对以后必须维护这份成果的人，我敢押注它是对的吗**？ 代码和其他交付物都用这个问题检验自己能否为它们负责。
- **我已经不再练习什么了**？ Osmani 可以接受少做一些日常调试，希望这是自己有意作出的选择。

编码加快以后，瓶颈转向确认结果是否正确。Boris Cherny 的做法是“给 Claude 一种验证自己工作的方式”。端到端测试、基于属性的测试、实际操作应用，都可以让代理自行修改、运行检查、读取结果并再次尝试。人的精力可以更多用来设计这个循环和检查证据，把逐行阅读留给需要深查的地方。验证也可能被一并交出去，“有什么证据支持结论”很容易变成“检查变绿了吗”。如果测试和实现犯了同一个错误，功能坏了也能亮绿灯。一项检查通过只说明一项性质，接着要问它证明了什么，又漏掉了什么。

**提前定义什么叫“已验证”**，因为事后总能为到手的结果找到解释。把完成条件落到可核对的证据上，例如某项测试通过、一张截图、一份日志或一条追踪记录。收到完工通知，先看代理实际执行的命令及其输出，再看总结。Claude Code 可以把全新上下文中的子代理审查固定到验证循环里。复杂功能经模型实现、自己审过一遍之后，Osmani 还会问“我漏掉了什么？”，模型常能再找出两到三点。Claude Code 团队的代码审查经验是，如果说不出这些检查会漏掉什么，就安排一次深入审查。代理综合了 50 通客户电话，就抽查几份源材料。做了竞品分析，就回看它引用的原始材料。建议依赖某个数字，就重新核对它的计算方式。建立验证流程的成本降了，什么证据足以支撑结论仍要自己判断。

一份 600 行的拉取请求，扫过结构、看到变量名合理和测试通过就点批准，往往只能发现自己本来就知道要找的问题。事务边界上细微的执行顺序变化，或从没考虑过的边界情形里被反转的默认值，都可能溜过去。写代码和审代码是两种技能。用审查人写的代码的标准读差异，再追查代理选了哪些默认设置、把哪些事项划出了范围、两项要求冲突时重新解释了哪一项。让代理列出做过的决定和采用的假设，“进展顺利”的总结通常不会交代这些。审代码时可以随机挑几行，试着解释为什么这么写。审文档时可以关掉文档，凭记忆写出主论点。长会话后可以让 Claude 写变更报告并在末尾出题，全答对才合并。

代理也能帮人把注意力集中到需要判断的地方。Osmani 用它梳理开源项目新收到的拉取请求、找出可能违反项目规范的内容、标出可能需要自己关注的地方，最后由自己判断变更有没有用合适的方式解决正确的问题。他把代理生成的成果与自己敢署名认可的成果之间的差距称为**编排税**。待审成果堆得比自己审得快，再开一个会话也帮不上忙。可以收紧检查标准，减少需要亲自介入的内容，也可以降低产出速度，让审查跟得上。

人的心智模型更多用在任务的两端，开头交代任务和上下文，结尾审查产出。写提示词因此也是批判性思维的一部分。向同事提含糊的要求，往往会被追问，才意识到自己还没想清楚。代理常会自行填补空白，交来一份看似完成的成果。Osmani 称之为**意图债务**，自己没亲手写的成果里，可能藏着从未说清的目标、约束和理由，这些意图只能由提出任务的人确定。提示词反映了你对问题的理解，表达不清可能意味着自己也没想清。求助前先用自己的话写任务简报，交代受众是谁、哪些内容超出范围、什么才算完成。第二轮纠正后仍达不到目标，就停下局部修补，重写提示词。

Andy Clark 区分了委托 AI 和与 AI 协作。协作时，提示词让输出更清楚，输出又让下一轮提示词和自己对问题的理解更清楚。可以请代理就它没弄懂的地方采访自己，结束时对问题有了更清晰的心智模型，本身也是成果。多代理接力时也要留意它们实际读了什么。如果每个代理只接收前一个代理的摘要，传到第三个代理时，它可能根本没读过原始文档。输出也需要自己的质量标准。Osmani 用 AI 尝试过多种创作，多数达不到他的标准，因而没有公开。格式整齐、语气自信已很常见，他用自己是否愿意署名来决定是否发布。把未达标的具体原因写进共享配置、钩子或测试，可以让质量标准反复生效，也让自己更会辨认问题。

再过一两年，模型也许就能发现人能发现的问题，Osmani 本来也主张把越来越多的检测交给代理。每项任务能信任代理到什么程度，仍需根据实际产出来校准，因为模型容易犯的错误会变。Anthropic 对内部工程师和研究人员的研究将其中的陷阱称为**监督悖论**。“监督 Claude 所需的，恰恰是那些可能因过度使用人工智能而退化的编程技能。”要做什么、为什么值得做、会影响谁、为此愿意牺牲什么，代理可以陪人推敲，作取舍和为发布负责的仍是人。

日常可以选几项适合自己的做法。每周一次，不用代理，亲手写一点代码，或亲手完成一项忘了怎么做就会很麻烦的真实任务，把它当作了解自己能力的“校准练习”。每月一次，写下已经不再亲手做的事，逐项决定哪些可以继续不做，再问自己“如果没有人工智能，你会有多不知所措？”写作碰到陌生说法时，Osmani 会做一点研究，弄懂它在上下文里为什么有用。认真检查代理的工作会占用实际工时，值得列进日程。想保留的技能就继续亲手用，停练后它们可能比预期退化得更快。

最后可以把提问和验收连成一次练习。问代理前写下自己预计会发生什么，等它完成后再写下一项它没有检查的内容，看看这两笔记录是否改变了自己阅读输出的方式。
