这篇 claude.dev 博客（2026-10-08，Lance Martin、CJ Avilla）讲的是**后台定时运行的 agent 自动化怎么才不出错**。他们用 Claude Managed Agents（beta）做了一个参考实现：按计划读取 Slack 频道和 GitHub PR，记录自上次运行以来的变化，把你需要知道的事发到一个 Slack 频道。核心结论是：这类自动化难的不是“让模型总结”，而是**没人盯着的时候，它会悄悄丢掉某个来源、重复或漏报、用过时状态说错话、忘了你的偏好**。文章把对策压缩成六条规则：

1. 每个来源按**书签**读取，不用固定时间窗。
2. 读取失败要报告为“读不到”，**绝不能当成平静的一天**。
3. 发帖前**重查每一项**的实时状态。
4. 只有 Slack 确认发出后，才更新书签和台账。
5. 每次运行都从 agent **无法修改**的存储里重读偏好。
6. 只读的地方给只读权限，并给每次运行设**花费上限**。

## 结构：六个组件

- **来源**：要读的地方的命名清单（默认 Slack 频道和 GitHub PR，列在偏好文件里）。
- **目的地**：agent 唯一可以写的地方（一个 Slack 频道，每次发一条带日期的帖子）。
- **Agent**：`agent.md` 里的模型、工具和运行步骤。
- **计划**：cron 表达式。
- **记忆**：你的偏好 + agent 自己的状态。
- **护栏**：只读权限和单次花费上限。

整个配置是一个目录（`agent.md`、`deployment.md`、`environment.yaml` 网络白名单、两个记忆库 yaml、`vault.yaml`、Slack manifest），用 `ant apply` 在 Claude API 工作区创建资源，ID 写进 `claude-lock.json`，之后在 Anthropic 的基础设施上按计划运行，本机不需要常驻。

## 来源：凭证、书签、失败

- **凭证放在 vault 里，真实值不进沙箱**。GitHub 走 MCP，代理在沙箱外按 URL 匹配凭证；Slack 用 bash 里的 curl 调 API，沙箱里只有一个占位符 `$SLACK_BOT_TOKEN`，请求离开沙箱时平台才替换成真 token，且只对允许的主机（`slack.com`）生效。
- **从上次停下的地方读**：常见错误是让 agent 读“过去 24 小时”——晚跑会留空档，早跑会重复。改为每个来源一个书签：每次结束时把读到的最新条目时间戳写进 `bookmarks.json`（如 `"slack": "2026-09-14T13:02:11Z"`），下次从这里开始，窗口自动伸缩。书签存在名为 state 的记忆库里，平台把它挂载到每次运行沙箱的 `/mnt/memory/` 并跨运行保留。
- **别把读取失败当成安静的一天**：MCP 服务器挂了或 token 过期时，运行照样开始，只是少了那个服务器的工具；会话里记了错误，但 agent 看到的是“什么都没有”，于是报告“没有新消息”。对策写在 `agent.md` 里：来源失败时**书签不动**，用其他来源照常写简报，并在结尾加一行说明哪里没读到（“本次无法读取 PR”）。

## 目的地：确认发出再记账

Agent 用 bash 里的 curl 调 `chat.postMessage` 发帖，bash 工具默认无需审批，`slack.com` 也在环境白名单里。风险在于记录与实际不一致：**记了一条没发出去的帖子，书签就前移，那些条目永远不会被报告；不确定是否发出而重发，读者就收到两份**。三条规则：

1. 发帖前在频道最近消息里找今天的标题，已经有了就不发；
2. 只有 Slack 返回 `"ok": true` 和消息 `ts` 才算发出；
3. 确认之后才更新台账和书签；结果不明时标记为“maybe posted”，其他什么都不改，保证不丢东西。

每次运行在记忆库里留一份 `runs/<date>.md`：发帖前标“posting”，之后标“posted”加消息 ID，或“maybe posted”。

## Agent：简短、发前重查

- `agent.md` 的 frontmatter 指定模型（`claude-sonnet-5-5`）、GitHub MCP、关掉 web_search 和 web_fetch。**MCP 工具默认要审批，而后台运行时没人来批**，所以 GitHub 工具集设为 `always_allow`，同时 GitHub token 是只读的。
- **让简报保持短**（运行步骤第 4 步“Decide”）：一条内容只有在读者今天就会据此行动、或会改变他马上要做的决定时才入选；拿不准就不写；多数日子只有几条，有时为零。“12 个待审”这种计数不算条目，要链接的是被卡住的那几个。台账里已有且仍未关闭的，只写一行“still waiting, day 3”，不重新报告；已关闭的直接去掉；偏好文件里退役的话题不要再提。
- **发帖前重查**（第 5 步“Verify”）：读取到发帖之间世界变了。每一项都在发帖前重查实时来源——已解决就删，仍开着但有变化就改，确认不了就删并记入运行记录的 cuts。原文的说法是：**一条过时的“仍在等你”比漏掉十条更伤信任，所以不要含糊其辞，要么断言要么删掉**。所有链接都从来源自带的链接字段复制（PR 的 `html_url`、Slack permalink），绝不手工拼接。

## 计划：deployment 与时区

在 Managed Agents 里，agent 只是一份配置，由 deployment 来运行：它指定 agent、环境、每次运行的第一条消息，以及计划、vault、记忆库和预算。每次 cron 触发，平台都开一个全新会话。示例是工作日纽约时间 7:32（`32 7 * * 1-5`）。可以用 `ant beta:deployments run` 手动触发测试。

常见 bug 是 **agent 按服务器时区算日期，把今天早上叫成“昨天**”。所以 `timezone` 字段决定何时触发，而第一条消息的第二行明确告诉 agent 用哪个时区算日期。

## 记忆：两个库，分开读写

每次运行都在全新沙箱里，没有记忆反馈就留不下来；但过时的记忆也会误导——把已解决的报成仍在等，或把仍开着的因为“已经报过”而丢掉。

- **preferences**（你的，agent 只读）：读哪些频道和仓库、排除什么、长度上限、目的地、何时停止。
- **state**（agent 的，可读写）：书签、已报告条目的台账、每次运行的记录、它对你偏好提出的修改建议，以及每个来源的行为笔记（如“只返回最新 50 条”）。

两条做法：

- **每次运行重读偏好**：常见问题是把偏好的一份拷贝烤进 prompt，结果一直执行你早已改掉的规则。读不到偏好文件就应该停下来说明，而不是用默认值继续跑。
- **用台账记录报过什么，并报告变化**：`ledger.md` 每行记录报告日期、来源、一个不会变的 ID（Slack 消息时间戳或 PR 编号）和最新已知状态，避免简报自我重复。

## 护栏：限制能做什么、能花多少

- **限制能做什么**：agent 读的是别人写的消息和 issue，这些文本可能被当成指令。所以要限制它“照做”时能造成的后果：GitHub token 和偏好库只读，环境只能访问白名单主机。被植入的指令仍可能改变简报内容（包括通过 agent 跨运行保存的笔记），但改不了 GitHub，也改不了你的规则。例外是 Slack——同一个 token 也能发帖，所以只把 bot 邀请进它确实需要读或写的频道。
- **用真实运行设定花费上限**：先设为正常运行成本的 3–5 倍，看到真实数字后再收紧。注意**触顶的运行是暂停而不是失败**（停止原因 `budget_reached`），上限设太低看起来就像简报变安静了。预算写在 `deployment.md`，金额是以美分为单位的字符串（`"500"` 即 $5.00），每次运行都拿到全额。
