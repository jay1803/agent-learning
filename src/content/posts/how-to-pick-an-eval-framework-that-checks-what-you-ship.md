选 eval 框架的关键不是比谁的指标多，而是先说清楚你要评**哪一层**（最终答案、单步、工具选择、整条路径、对话、成本），再看框架在“跑得稳、能拦发布、能从线上失败回流数据”这几件事上替你省了什么、还留给你什么。作者（Sergii Makarevych，发于 2026-11-21）只依据公开文档、仓库页面和论文，没有自己跑模型，厂商说法单独标为“声称”。最反直觉的一句：**grader 本身是被测系统的一部分，不是中立的尺子**，所以每个 eval 要有两个数——产品有多好，以及 grader 与人的一致程度。最常见的自欺方式，就是用一个没校准过的 judge 打出一个自信的分数。

## 共同骨架与四个名词

- eval 是可重复的检查：在一组输入上跑系统、给每个输出打分，让改动用数字而不是 demo 印象来判断。语言模型“流畅地出错”，读一个好答案说明不了接下来一百个。
- 几乎所有框架都要你提供同样四样东西：**Data**（用例，必要时带标准答案）、**Target**（被测对象：一次模型调用、chain、完整 agent、检索器或整条 trace）、**Judgment**（代码规则、模型评委、带概率的决策模型、成对比较或人工）、**Run**（保存下来可比较的实验）。
- grader 有四种形态：代码规则、第二个模型当评委、返回选项加概率的类型化决策模型、人。trajectory 是 agent 一次运行的完整有序记录（prompt、模型调用、带参数的工具调用、检索到的段落、最终答案），span 是其中一步。
- 可评的层级由小到大：最终答案、单步、工具选择（对的工具、对的参数、结果被用上）、整条路径（任务完成、浪费步数、是否按计划）、整段对话、检索与生成分开、系统账单（成本、延迟、每次成功的 token）。
- 随后每一层都是针对上一层提出的问题逐级放大的：共同结构 → 代码优先 → 配置优先 → 实验平台 → 可观测性优先 → 单一用途 RAG 指标。

## 第二层：代码优先的 agent eval

**Inspect** 是深入样例：dataset + solver + scorer。solver 是能多次调用模型、用工具、读文件、在沙箱里跑代码、跨轮记忆、交给子 agent 的循环；沙箱可以是隔离机器或容器。scorer 有精确文本匹配、相似度（含困惑度）、模型评委、自定义代码读完整 transcript 四类。模型不写在 task 里，运行时用命令行指定，每个样例产出一份含 prompt、模型调用、分数的 transcript 日志。限制：几乎没有现成的 trajectory 和 RAG 指标，工具正确性、计划质量都要自己写 scorer；没有托管的实验比较和标注队列，也没有线上打分闭环。

- **DeepEval**：pytest 当 runner，大量内置指标是护城河。trajectory 靠 tracing 一等公民：给函数加 observe，每个 golden case 跑一次 agent，再对整条路径评任务完成、浪费步数、计划遵循，以及每步工具选择和参数正确性。检索与生成、多轮对话也是一等公民，评委模式有纯模型评委、混合（模型写理由、决策模型裁决）、纯决策模型三种。限制：路径指标依赖它的 tracing，成千上万次评委调用很花钱，没有 repeats 原语，也没有沙箱。
- **Pydantic Evals**：类型化的 case 与期望输出，可以带 per-case 评委（同一批里一个菜谱要求无肉，另一个要求无麸质，只共享通用检查）。report 级评估器算混淆矩阵等汇总；trajectory 检查是确定性的、基于 span（期望的工具集合、有序序列、参数和预算检查），不调模型；在线评估原生支持采样打分。限制：只看得到本地执行的工具，现成的 RAG 与安全指标是 rubric 或第三方集成。
- **SkillEvaluator**（新兴）：评的是 skill 目录本身及其对 agent 行为的影响，三层可单独跑：形式、安全与可加载性（厂商声称 500+ 静态规则）；与其他 skill 的重叠（节省上下文）；有无 skill 的沙箱对比，报告 skill 带来的提升和 token 成本。约 4000 star 但标为实验性、无服务承诺，建议与代码优先框架搭配而不是替代。
- 结论：这一层真正的差别是 **solver 层，不是指标数量**。需要工具加沙箱加重试，从这里开始；需要不写 scorer 就有 trajectory 数字，从指标目录那一边开始。

## 第三层：配置优先的 harness

- **lm-evaluation-harness**：开放榜单的后端，任务大体是 YAML（数据集路径、Jinja prompt 模板、输出类型、few-shot 数、过滤链、指标）。原生只评基础模型的最终输出，没有 trajectory、工具、检索拆分或多轮，这是有意为之。优势在稳定性：每样本重复加多数投票、分别设置 prompt 采样和权重随机的 seed（并建议随分数一起报告 seed 和重复次数）、响应缓存让重跑便宜。没有评委模型，所以也没有评委信任问题，但对开放式质量没有灵活性；它的产品是可比性，不是产品回归。
- **Promptfoo**：同样的矩阵（prompt × provider × 用例）写在 YAML 里，目标更宽（工具调用有效性、trajectory 断言、RAG 断言、对话相关性），断言更丰富并有红队测试；结果留在本地，没有中央实验历史，也没有基于采样的线上打分。
- **OpenAI Evals** 只当设计参考（数据、逻辑、配置三层分离值得借鉴），托管平台在退役，新项目不要采用；**HELM** 只当覆盖面检查清单（场景 × 适配 × 指标，缺一格比如非英语是任何 runner 都补不上的缺口），已进入维护模式，榜单只读不能当发布闸门。
- 结论：配置优先买到的是可比性和速度，**不是深度**。别用只看最终文本的 harness 去评 trajectory，然后奇怪为什么修了不涨分。

## 第四层：实验优先的平台

- 实验是一次不可变的保存运行（每个输入、输出、分数、trace），数据集版本是固定快照，避免之后编辑悄悄移动球门。
- **Braintrust**：data + task + scores 形成 experiment；层级通过 span、trace、session 分组实现；没有内置命名的工具正确性 scorer。评委信任来自“手动输入测试 → 数据集样本 → 真实线上日志”三阶段，scorer 和 prompt 都有版本。稳定性方面刻意单薄：每行每实验只跑一次，建议每个实验只改一处；PR 跑冒烟、合并后跑全量。闸门明确：PR 上跑 eval 并把分数贴为评论，线上规则按范围、过滤和采样给实时流量打分。限制：核心是商业托管，领域指标要自己写，没有重复统计。
- **MLflow GenAI**：自托管版本，数据集存在带 SQL 后端的 tracking server，可从 trace 里选取并记录期望来构建；内置评委目录大得多（回答质量、RAG、工具调用、多轮会话），评委校准是可命名、可度量的（用人工反馈对齐，在自动化之前把一致率做高）；闸门是 pytest 原生的，把评估标记为回归测试，失败就让构建失败。限制：需要搭服务器和 SQL。
- 采样建议：对精心准备的测试集全量打分，线上流量采样；**按风险而不是均匀采样**，新 prompt 和新工具先高采样、分数稳定后降低；给线上打分固定一个版本，让下一个版本在历史上测试，避免改 rubric 悄悄重打上个月的分。
- 结论：平台赢在“失败 → 数据集 → 闸门”的回路，不在指标聪明。好指标如果没有版本化数据和闸门，回归照样上线。

## 第五层：可观测性优先

- trace 是一次请求的完整执行记录；在线评估是在没有标准答案时对线上 trace 打分，离线评估是在发布前对带期望答案的数据集打分。
- **Langfuse**：把 traces、sessions、prompts、scores、datasets、experiments、monitoring 的闭环文档化得最完整。分数可以挂在单个 observation、整条 trace、session 或数据集运行上；评委映射变量、评估器有版本并能对历史批量重评、人机一致性有校准视图，还有采样、花费上限和事前成本估算。限制：指标库有意做薄，需要深度时要把 RAG 或 agent 指标代码当分数推进去；实验任务代码在本地或流水线运行。
- **LangSmith**：同样 trace → dataset → evaluator，但仅托管，对 LangChain 技术栈最深；多出成对比较和线程级对话评分，无参考的检查在线离线都能用，需要参考答案的只能离线。**Phoenix**：评估器就是命名输入输出的普通函数，预置模板覆盖忠实度、幻觉、工具选择与调用等，trajectory 与对话是一等公民；没有原生的带采样的线上规则引擎，也没有内置流水线闸门。**TruLens**：反馈函数挂在 record selector 上，招牌是上下文相关性 + 有据性 + 答案相关性的 RAG 三检查，卖点是已发布的评委基准和 rubric 调优，更适合当大回路里的指标提供者。**Evidently**：描述符函数给表格的每一行打分，声称 100+ 内置检查，数据集级测试套件可接入每次 push 的流水线；没有 trajectory 评估器，调试靠看 dataframe。
- 校准习惯：先让人标一个小集合再测每个评委，一致率低于团队标准说明要改 rubric 或示例而不是产品；评委改动后对历史重打分，并排比较新旧结论，翻转很大说明新 prompt 收窄或放宽了规则；事实检查和风格检查拆成不同评估器，因为混在一起会让一个数字掩盖两处分歧。
- 结论：可观测性告诉你发生了什么，**不会自己告诉你好不好**。要挂上带校准和阈值的显式评委，否则 trace 只是“没有裁决的电视”，延迟面板一片绿，质量却在悄悄漂移。

## 第六层：单一用途 RAG 指标

- **Ragas** 是指标库，不是平台。核心思路是把检索和生成拆开分别打分，让修复落在正确的地方：低精度就修搜索，低忠实度就修生成或 prompt。四个核心检查：忠实度（回答里有多少断言被检索上下文支持）、答案相关性（生成问题加嵌入相似度，需评委和嵌入模型）、上下文精度（好段落是否排在前面）、上下文召回（参考答案被覆盖的程度，必须有参考答案）。
- 限制说得很直白：按样本异步打分，没有重复、没有 pass@k、没有时间/token/成本上限、没有重试，同一输入重跑分数会有小差异；结果是控制台加本地文件，闸门是手写阈值，没有成本追踪、沙箱、tracing 和线上闭环。固定评委模型和温度，小集合跑两遍记录波动之后再信任闸门。旧版指标路径已弃用，只照抄新式 collections API 的例子。
- 常见搭配：放进配置矩阵里快速回归检索改动；放进 pytest 评估 agent 加 RAG 应用；作为平台里 trace 的评估器；大规模评测里先用廉价分类器（字符串或 ID 重叠）跑全部、再让模型评委只跑不确定的那部分。

## 决策表（先问题、后品牌）

- 在公开集上比哪个模型或 prompt 好：lm-harness（并记录 seed、重复次数、过滤链）。
- 流水线里的快速回归和多模型比较：Promptfoo。
- 带工具和不安全代码的 agent：Inspect（沙箱、限制、完整 transcript、重复方差）。
- 像单元测试一样让构建失败的 Python 检查：DeepEval（指标只留少数几个、固定评委、噪声检查标 flaky）。
- 类型化契约加 per-case rubric：Pydantic Evals。
- 发布历史、切片和线上失败变成新用例：能接受托管选 Braintrust，必须自托管选 MLflow。
- 调试路径并监控线上流量：重视自托管用 Langfuse，已在 LangChain 栈用 LangSmith，span 函数合适用 Phoenix。
- 评委质量是瓶颈：TruLens 的反馈模式加校准做法，放进上面某个回路里。
- 表格行级质量闸门：Evidently。只要检索质量：Ragas 放进某个回路。
- 如果验证检查没通过，意味着应该换一个“货架”，而不是在原地更用力地调。

## 作者的团队规则

- eval = Data + Target + Judgment + Run，哪怕手工也要把四样都建起来；先说层级再说品牌。
- grader 需要自己的评分：自动化之前先测与人的一致率，再固定版本。
- 代码优先适合有工具和状态的 agent，配置优先适合基准数字与快速矩阵；基准 harness 买到可比性，买不到调试和闸门；平台买到版本化数据、对比、闸门和线上回路，买不到统计重复；trace 优先的工具需要显式评委加阈值；RAG 指标买到的是故障定位，要分开跑检索与生成检查并配合一个管历史的回路。
- 每条规则都要能改变构建内容或阻止合并，不改变行为的规则就删掉。

## 局限

- 全部来自公开文档的综述，没有实测，厂商数字（如 SkillEvaluator 的 500+ 规则、Evidently 的 100+ 检查）只是声称；作者也特别说明没有跑一个贯穿案例，是怕团队把它当模板照抄。
