这篇文章（2026-09-28，claude.dev Blog 的 Playbooks）的核心是：设计评测和针对评测做优化都很容易自欺欺人，所以要把防自欺的纪律（真实任务分布、校验评分器、划分训练集与测试集、每轮只改一处）固化成流程。claude-api skill 里新增的 `/claude-api build-eval` 和 `/claude-api hillclimb` 就是这套流程的自动化版本。最反直觉的两点：在评测里卡住不涨，常常是评测本身（任务或评分器）有问题，而不是模型；而在评测已经饱和时，“同等效果下降低成本”是最稳的优化目标。

## 好评测的四个特征

1. **任务贴近生产**：不能因为好生成、好打分就选任务，要代表你真正关心的分布。
2. **更强模型、更多思考应得更高分**：若不是，多半是任务有歧义或评分器没校准。
3. **前沿仍有“可通过”的余量**：最强模型、最高 effort 应明显低于 100%，否则无法判断改动效果。差距不能来自“不可能或有歧义的任务”，典型迹象是某个任务无论重复多少次都全失败；好任务应满足“两个领域专家会给出同样结论，且评分器检查的一切都写在任务里”。
4. **运行间方差低**：高方差常来自歧义任务或对同一输出给出不同结论的评分器，也可能藏在配置里（effort 没有被一致应用），或环境里（上一次试验遗留的文件、git 历史把答案递给了 agent）。

**对抗式采样的陷阱**：模型能力是参差不齐的，如果只挑“今天这个模型会失败”的案例，测到的就是这个模型的“失败指纹”，而不是什么真正困难或有价值。正确做法是挑人判断为难的案例（要能说出为什么难），或来自生产流量、bug 报告和工单的真实失败。但也不要盲信用户流量：用户往往只试自己预期能成功的事，纯流量分布可能偏容易。

## /claude-api build-eval：访谈、建在你的代码库里、关键点要你批准

- **取样优先级**：生产对话记录（先问保留期和敏感数据）→ bug 报告与支持工单 → 你手写的 5–10 个案例 → 从代码库合成的案例；合成数据要以你提供的少量真实样本为锚。它会生成一个页面展示所有输入，等你确认。
- **评分器选最便宜且合适的**：输出受限就用程序化检查（精确匹配、固定标签集、JSON schema、测试通过）；输出开放就用 LLM-as-judge，评分标准写成“可核对的陈述”而不是 1–5 分；如果有基线可比，则让评委以随机顺序同时看两份输出、不告知哪个是基线，选更好的；评委模型不能是被测模型。
- **先验评分器**：它会给几个案例打分并问你是否会打不同的分，“读一批已评分的记录再相信评分器”是最常见的纠错点。
- **产出物**：案例、评分器、运行器、每个案例一行 JSON 加一份完整记录，以及一个本地静态页面（默认不联网）；基线分数带置信区间。
- **自动诊断**：对同一输出重复评分检查结论是否改变；检查超时、API 报错、答案被截断，避免把基础设施噪声当成模型方差；基线已达约 95% 以上时警告，建议把爬坡目标转向成本或延迟。

## 爬坡（Hillclimbing）：选对表面，再防过拟合

**适合爬坡的表面**：改起来便宜（提示词、skill 这类文本比改整个 agent harness 容易回退）；可归因（分数变化要能直接对应你改的东西，例如 skill 触发率对应 skill 描述）；目标范围明确（接近饱和的评测或“泛泛地改进 harness”最容易卡住，成本是一个普遍好用的目标）。

**过拟合怎么发生**：评测会“泄漏”进 harness。例如评测任务受益于 OCR，而生产里几乎用不到，harness 加了 OCR 工具后评测分上去了，生产毫无变化；或爬坡给特定评测样例的边界情况加了功能。三条对策：

- **切分训练/测试集**：爬坡器只能读训练集，测试集永不可见；训练升而测试持平就是过拟合警告。
- **不要把失败内容贴进提示词**。
- **从结构上让答案够不着模型**，防止它“奖励作弊”直接找到答案。

**hillclimb 的流程**：先问优化目标，再随机切分训练/测试；开始前检查评测噪声是否小于你愿意采取行动的最小提升，否则建议加重复次数或案例；每轮读上一轮训练记录，只提一个补丁，而且从根因出发（重写造成问题的段落或补缺失规则，而不是改措辞），使修改的效果能高于噪声；训练升测试平则判定过拟合并回退，回归也回退，双升才保留。分数停滞 2–3 轮后，它**不改东西，只把剩余失败按根因分类**，这能暴露有歧义的案例、harness 错误和方差。最终代码停在测试集上最优的版本，报告带置信区间，提升落在噪声内时会明确建议不要合并。

## 两个案例

**降本（内部客服基准，44 张工单，30 张搜索、14 张留出**）：起点 Opus 4.8、默认高 effort，决策准确率 74.4%，每张工单 4.6 美分。先审计提示词，去掉强制的工具调用仪式、草稿步骤和互相矛盾的规则；再换成 Opus 5.5 低 effort，准确率 87.8%，成本 1.9 美分（部分来自价格：输入/输出便宜 20%，缓存读取便宜 60%）；因为已经过线，又降一档试 Sonnet 5 低 effort，88.9%、约 1 美分；最后加入路由规则和退款上限的交叉引用，提到 98.9%、成本不变。**留出的 14 张工单上，最终配置 90.5%，原配置 78.6%，成本约为原来的五分之一**。

**提升性能（claude-api skill 自己的评测，由文档派生**）：起点 66%。给爬坡器文档和 SDK 的访问权，让它能自己找错、纠错。
- 先发现 skill 缺了 8 个特性的覆盖，补上后 74%，再修 C# 与 Java 的类型表，77%。
- 停滞后做根因分类：**内容其实都在，是 Claude 依旧写训练里记得的旧 API 形态**（比如 API 在新 Opus 上已拒绝固定 token 预算的 extended thinking，应改用 adaptive thinking；web search/fetch 工具也是旧版本）。对策是在 skill 顶部加一张“旧写法→新写法”对照表，并把 C#/Java 关于固定预算 thinking 的警告挪到 adaptive 示例之前，提到 80%。
- 还有任务怎么补内容都不涨，那是例子或评分器本身有问题：一个任务要求捕获一种错误，评分器却要求至少三层链；另一个评分器的说明与文档矛盾，实测真实 API 证明文档才是对的。修掉后连同更多 skill 编辑，到约 88%。

## 值得带走的做法

- 任务不涨时，先怀疑评测（歧义任务、坏评分器），再怀疑模型。
- 用“训练升/测试平”识别过拟合，而不是只看总分。
- 爬坡目标选“成本不变下提质量”或“质量不变下降成本”，换小一档模型再复测往往能同时拿到两者。
- 当 skill 或提示词“内容都有但模型不照做”，问题可能是模型先验里的旧写法，要给它明确的旧→新对照。
- 用法：先 `claude update`，然后在 Claude Code 里运行 `/claude-api build-eval`、`/claude-api hillclimb`。
